## 5. Architectural Recommendations for HORUS Based on Prior Art

* **Delegate multi-step mission plans rather than atomic commands**: As demonstrated by [TypeFly](https://typefly.github.io/) and the [UCI MCP Drone Server](https://arxiv.org/html/2601.15486v2), issuing individual flight commands over a network link fails when latency spikes or connectivity drops mid-maneuver. Have the server-side AI commander translate natural-language requests into a structured, self-contained mission script or behavior tree (e.g., `search_area` -> `detect_target(class)` -> `record_finding` -> `return_to_launch`) that the onboard companion computer executes locally from start to finish.
* **Implement an onboard Store-and-Forward buffer with event-driven synchronization**: Adapting the database architecture from the [UC3M Edge-Cloud BVLOS platform](https://arxiv.org/html/2507.15049v1), maintain a local SQLite buffer on the drone's companion node that stores CNN detection metadata (class, confidence, bounding box, cropped keyframe, GPS/NED coordinates, and timestamp) whenever the connection to the commander is degraded or lost, then flushes queued findings automatically when the link recovers.
* **Enforce deterministic safety limits and native RC/GCS override**: Following [Neuro-LIFT](https://arxiv.org/html/2501.19259v1), [ASMA](https://arxiv.org/html/2409.10283v4), and the [PX4 ROS 2 Control Interface](https://docs.px4.io/main/en/ros2/px4_ros2_control_interface), place a deterministic validation layer on the companion computer that checks every AI-generated action against geofence bounds, altitude floor/ceiling, maximum velocity, and battery thresholds before sending setpoints to PX4, while relying on PX4's native mode-switching state machine so a human operator's RC transmitter or QGroundControl override immediately preempts autonomous execution.
